# 拍照饮食 App → Recovery Pocket

本轮实现的是 Recovery Pocket 的能量读取和日收支；还没有创建完整拍照饮食 App，也没有调用 LLM 或上传食物照片。

建议使用原生 iPhone 饮食 App 写 Apple 健康的 `dietaryEnergyConsumed`，Pocket 只读。两个 App 各自请求权限，不共享 API Key、相册或服务器账号。网页/LLM 服务本身不能直接写手机的 HealthKit；照片识别结果由原生 App 接收、确认后写入。

## 每餐结构

使用 `PhotoMealHealthWriter.swift` 中的 schemaVersion 1 结构：

- mealID：一餐固定 UUID，重复识别或改份量保持不变。
- revision：从 1 开始递增，修改餐次时提高版本。
- eatenAt：实际用餐时间，ISO 8601 带时区；不是上传时间或未来计划时间。
- foods：食物名称、估计克数、kcal、中低高范围和计算依据。
- totalKcal/lowerKcal/upperKcal：逐项相加，中值位于范围内。
- assumptions/questions：不确定份量、油、酱料等信息。范围不是统计置信区间。
- userConfirmed：份量与关键未知项经用户确认后，才允许写健康记录。

AI 分析草稿不自动写入。输入拍照/包装/餐前餐后重量后，应优先使用可核验包装营养表或食物数据库，并明确生重、熟重、可食部及份量。看不到的油/酱不假称已测出；不要承诺照片能精确算卡路里。水等零能量项目允许显式 0，缺失不能代替 0。

## 写入与去重

1. 调用系统写入权限请求，由用户自行选择允许。需要饮食 App 的 HealthKit entitlement 和相应 Info.plist 描述。
2. `HKMetadataKeySyncIdentifier = rfg-meal-<mealID>`，`HKMetadataKeySyncVersion = revision`。同餐修订使用同 ID、更高版本；新餐使用新 ID。
3. 写入的主数值为 kcal。自定义元数据 `studio.rfg.food.estimateLowerKcal` 和 `studio.rfg.food.estimateUpperKcal` 同样为 kcal。
4. Pocket 每次从健康记录重建日汇总，不在刷新时累加旧缓存；按 UUID 和同来源餐次版本去重。饮食来源只选一个，避免 Keep/其他 App 导入同一餐重复计算。
5. 日收支只传播饮食估计范围，尚未量化手表消耗误差；范围不能称为真实缺口的置信区间。

参考写入器已按 iOS SDK 进行类型检查，**没有运行写入授权或真实 HealthKit 保存**。生产饮食 App 仍需处理删除餐次、撤销确认、离线队列、重试、权限失败和新版 API 兼容。删除必须删除本 App 创建的原样本，不能把删除当作写入 0；Pocket 刷新后重新汇总。

## AI 分析提示词骨架

你是食物记录助手。仅分析用户提供的食物和包装信息，不作减重处方。识别食物、数量、熟/生重与可食份量；计算依据优先为可核验营养标签或数据库。无法确定份量、烹饪油、酱料或是否全部吃完时说明假设，列出最多两个对结果影响最大的确认问题。输出逐项 kcal 和合理估计范围，并确保总值与逐项一致；不得虚构称重或声称照片给出了准确热量。输出 schemaVersion 1 JSON 草稿，userConfirmed=false；确认状态和 mealID/revision/eatenAt 由 App 管理。不要替用户自动确认，也不要直接写健康数据。
